# SnapKYC Video

A small proof of concept of RBI-style video KYC (V-CIP): a customer does a live, recorded
video call with an agent, a **different person** approves it, and the customer gets a signed
"KYC done" token that anyone can check.

- **Live URL:** `https://snapkyc-video.onrender.com` *(free tier: the first load after 15 min idle takes ~50 s)*
- **Demo logins** (password: `demo1234`)

| User | Role | Use it to |
|---|---|---|
| `agent1`, `agent2` | Agent (maker) | Run calls |
| `reviewer1` | Reviewer (checker) | Approve / reject |
| `supervisor1` | Agent **and** Reviewer | Show that maker-checker is enforced by identity: can review others' calls, never their own |

## Demo flow (consent to token)

1. **Customer** (`/customer`): tick consent, allow location, enter dummy ID `9999 0000 1234`, join the call.
2. **Agent** (`/agent`): pick up the customer. Recording starts automatically once connected. Ask the 3 random questions, take a face snapshot, end the call, recommend approve.
3. **Reviewer** (`/reviewer`): watch the recording, compare snapshot vs mock photo, read the audit trail, approve.
4. **Customer** page now shows the token as a QR code. **Check page** (`/verify`): paste the token, see it is valid. Change one character and it becomes invalid.

To see the maker-checker block: run the call as `supervisor1`, then log in to `/reviewer` as `supervisor1` and try to approve.

## How the five rules are enforced

| Rule | Where |
|---|---|
| Consent first | `POST /api/customer/sessions` rejects without `consent: true`; consent text + timestamp saved |
| Customer is in India | Browser location saved with timestamp; server rejects coordinates outside India (`rules.isInIndia`) |
| Live call, not an upload | WebRTC two-way video; signaling only lets the session's own customer and claiming agent join the room |
| Call is recorded | Agent browser records (customer + agent picture-in-picture, both voices) and uploads it; agent cannot recommend until it is saved |
| Maker-checker | `rules.canDecide`: the reviewer must not be the agent who ran the call. Repeated in the SQL `UPDATE ... WHERE agent_id <> reviewer` so it holds even under a race. Blocked attempts are logged |

Every step is written to an `events` table with a timestamp and shown to the reviewer as an audit trail.

## Architecture

```
 Customer browser ──┐                          ┌── Agent browser
   (camera, GPS)    │   WebRTC video (P2P or   │   (records call,
                    │◄──── via TURN relay) ───►│    takes snapshot)
                    │                          │
          REST + Socket.IO signaling (SDP/ICE only, no video)
                    ▼                          ▼
          ┌───────────────────────────────────────────┐
          │ Node / Express server (Render)            │
          │  routes/customer  routes/agent            │
          │  routes/reviewer  /api/verify (public)    │
          │  rules.js  kycToken.js  mockSnapkyc.js    │
          │  signaling.js (Socket.IO rooms)           │
          └──────┬─────────────────────┬──────────────┘
                 ▼                     ▼
       Supabase Postgres        Supabase Storage (private bucket)
       sessions + events        snapshots + recordings, signed URLs
```

Session states: `consented → waiting → in_call → recommended → approved | rejected`.

```
client/src/pages/      Customer, Agent, Reviewer, Verify screens
client/src/lib/        api.js, call.js (WebRTC), recorder.js (MediaRecorder)
server/src/rules.js    business rules (pure functions, unit tested)
server/src/routes/     one router per role
server/test/           rules tests + a full API run through the approval gate
```

## Run locally

Needs Node 20+. No accounts needed: without env vars it uses an in-memory database and local file storage.

```bash
npm run install:all
npm run dev:server        # terminal 1 -> http://localhost:4000
npm run dev:client        # terminal 2 -> open http://localhost:5173
npm test                  # 14 tests, incl. maker-checker
```

Local demo password is `demo123`. Use separate tabs/windows for customer, agent and reviewer (logins are per tab).
Camera and location only work on `localhost` or HTTPS.

## Deploy (all free tiers)

1. **Supabase**: new project. Storage → create a **private** bucket `kyc-media`. Copy the **Session pooler** connection
   string (Project Settings → Database; Render needs IPv4), the project URL and the `service_role` key.
2. **Metered** (Open Relay): create an app, copy its domain (`<name>.metered.live`) and API key.
3. **Render**: New → Blueprint → this repo (`render.yaml`). Fill in `DATABASE_URL`, `SUPABASE_URL`,
   `SUPABASE_SERVICE_ROLE_KEY`, `METERED_DOMAIN`, `METERED_API_KEY`, `DEMO_PASSWORD`. Secrets for JWT signing are generated by Render.

Tables are created automatically on start. Secrets live only in Render env vars; `.env` is git-ignored (see `server/.env.example`).
Frontend on Vercel instead: deploy `client/` with `VITE_API_URL=<render url>` and set `CLIENT_ORIGIN=<vercel url>` on Render.

## What is faked or simplified

- **SnapKYC is mocked**: `/api/mock-snapkyc/verify` returns a dummy name, DOB and a generated placeholder photo, plus an
  HMAC signature that the server checks (imitating SnapKYC's signed response). Only the last 4 digits of the dummy ID are stored.
- **Logins are hard-coded** demo users with one shared password.
- **Token is HS256**: only this server can verify it, so the check page calls the server.
- **India check is a bounding box** on browser GPS; GPS can be spoofed and there is no IP cross-check.
- **Recording happens in the agent's browser**: if the agent's tab crashes mid-call the recording is lost.
- **No face match** (nice-to-have not done): the reviewer compares the snapshot and photo by eye.
- **TURN credentials are static in this deployment**: production would use Metered's API mode for short-lived credentials.
- **Place names come from OpenStreetMap Nominatim reverse geocoding** (free, rate-limited); if the lookup fails, only the coordinates are shown. The India rule itself still uses the coordinates.

## Changes after first build

- **TURN fix**: routed static TURN URLs directly to Metered's global media relay servers (`global.relay.metered.ca`).
- **Protected ICE servers**: `/api/ice-servers` requires an active session secret or staff login; public debug mode removed.
- **Customer leave flow**: leaving a call shows a dedicated status screen with options to rejoin or start over without false "under review" statuses.
- **Agent can end call anytime**: KYC officers can cleanly end calls at any stage with confirmation dialogs and guidance.
- **Incoming call popup**: phone-like notification card for newly waiting customers with gentle ringtone and auto-dismiss.
- **Encrypted route badge**: WebRTC stats detect whether calls connect directly ("🔒 Encrypted · Direct") or via TURN ("🔒 Encrypted · Relayed via TURN").

## What I would do next

1. Face match between snapshot and SnapKYC photo, plus a liveness check (e.g. BioChQ).
2. Sign tokens with ES256 and publish the public key (JWKS) so anyone can verify offline; issue as a W3C Verifiable Credential.
3. Server-side recording (SFU) so recordings don't depend on the agent's browser; encryption at rest + retention policy.
4. Cross-check GPS against IP geolocation.
5. Real staff accounts with SSO, rate limiting, token revocation list.
